# Case Study: Counterfactual — a Causal Decision Engine

## What this project concretely does

Three causal-inference modules, chained into one pipeline, each independently
runnable and each validated against a known ground truth rather than "the
code ran and the number looked plausible":

1. **Uplift** (`pipelines/01`) trains a CATE model (T-learner/X-learner) on
   randomized synthetic campaign data — 10 features, a Bernoulli(0.5)
   treatment assignment, and a known heterogeneous effect function baked
   into the generator. Output: a budget-constrained targeting policy,
   serialized to `policy.joblib`.
2. **OPE** (`pipelines/02`) loads that exact saved policy and estimates,
   from a *second*, differently-generated dataset (logs from a non-uniform
   production logging policy, same underlying reward model), whether it
   would beat the policy that actually produced those logs — using IPS,
   SNIPS, and doubly-robust estimators, with bootstrap CIs — without ever
   running a live test.
3. **GeoLift** (`pipelines/03`) measures a simulated geo-level rollout
   (donor geos + one treated geo, correlated synthetic trends with a known
   injected % lift) via synthetic control — a weighted combination of
   untreated geos that tracks the treated geo's pre-period trend, with
   placebo-based significance testing since there's no valid normal-theory
   standard error with only a handful of geos.
4. **The full chain** (`pipelines/04`) runs all three in order and — the
   detail that makes it one system instead of three demos — derives the
   geolift stage's injected effect size directly from OPE's doubly-robust
   estimate vs. the current policy's empirical value, instead of using an
   arbitrary config number. Output: one `report.html` with all three plots
   and a bottom-line table.

Every result type across all three modules shares one `EffectEstimate`
shape (`{method, point_estimate, ci_lower, ci_upper, std_error, n,
metadata}`), so a CATE model's output, an OPE value estimate, and a
synthetic-control lift are logged and compared identically.

This doc covers what each module measures, and the real bug found and fixed
in each — the mechanism, not just the headline.

The connective thread: every module's evaluation is checkable against a
literal, injected ground truth (`true_cate` in `common/io.py`,
`true_effect_pct` in the geo simulator, `true_policy_value` in OPE's
simulator) — not "the code ran and the number looked plausible." Both real
bugs below were only catchable *because* something known-true existed to
check against.

---

## 1. Uplift — who to target

**What it measures:** individual treatment effect (CATE) — for each
customer, "how much better off are they *specifically because of* the
treatment," not just "did treated customers do better on average." Built
with two meta-learners on top of plain scikit-learn regressors (T-learner:
two independent models, one per arm; X-learner: a second stage that imputes
per-unit effects and blends them by propensity).

**How it's judged** (`uplift/evaluate.py:16-44`): the Qini curve ranks
customers by predicted CATE, then at each top-`k%` slice compares treated
vs. control outcomes — rescaled by group size (`y_t - y_c * (n_t/n_c)`)
since the slice isn't 50/50 within itself. AUUC is the area between that
curve and the random-targeting diagonal.

**The honest finding, not a bug:** the budget-capped policy (top 30% by
predicted CATE) scored *close to but not clearly above* "treat everyone" on
`policy_value` (`uplift/evaluate.py:57-83`, IPW-reweighted average outcome
under the policy's decisions). Why: the synthetic reward has no
per-treatment cost term, so "treat everyone" looks artificially free —
there's no penalty for wasting a treatment on someone with negative CATE,
it just doesn't hurt overall average because their loss is small relative
to the population. In a real business case you'd subtract a per-treatment
cost, and *that's* exactly what would make targeted uplift beat blanket
treatment. Left uncorrected here deliberately, to keep the module a clean
CATE/Qini demo rather than layering in an arbitrary cost assumption — but
it's the kind of gap worth stating out loud rather than hiding.

## 2. OPE — is this targeting policy worth an A/B test?

**What it measures:** the expected value of a *new* policy (e.g. uplift's
output), estimated purely from logs generated by a *different*,
already-running policy — no live test. Three estimators, same core trick
(reweight by how much more/less likely the target policy was to take the
logged action than the logging policy was):

- **IPS**: `mean(match/propensity * reward)`
- **SNIPS**: same weights, self-normalized (`sum(w*r)/sum(w)`) — lower
  variance, tiny bias
- **DR**: adds a direct-method reward model (reuses uplift's `TLearner`)
  fit on a held-out fold, corrected by an IPS-style residual term —
  unbiased if *either* the reward model or the propensities are right.

**The bug** (`tests/test_ope_estimator_bias.py:58-73`): a test wanted to
check that a target policy resembling the logging policy gets more usable
logged data than one that doesn't — measured via
`effective_sample_size = match.sum()` (`ope/estimators.py:58`), i.e. "how
many logged rows had exactly this action." It compared the constant
policies treat-all vs. treat-none and asserted treat-all wins, reasoning:
"the logging policy treats high-`proxy_score` people more often."

That reasoning is about the **slope** of
`propensity = sigmoid(1.5*proxy_score - 0.5)` — true, but irrelevant to
the question. What decides which constant policy wins is the **population
average** of that sigmoid, which the `-0.5` **intercept** pulls below 0.5.
So more than half the logged actions are actually 0, and treat-none wins.
Slope (who gets treated *relatively* more) and level (what fraction gets
treated *overall*) are independent facts about a sigmoid — the bug
conflated them.

**The fix:** stop asserting a direction, derive it —
`majority_action = round(action.mean())` (line 66) — so the test can't
silently break if the intercept ever changes, and it's checking the actual
mechanism instead of an assumption about it.

## 3. GeoLift — did the real rollout work?

**What it measures:** a campaign's aggregate effect when you can't
randomize individuals — a TV spot, a geo-level push. Synthetic control
builds a weighted blend of untreated "donor" geos that best tracks the
treated geo's *pre-campaign* trend; the post-campaign gap between actual
and that synthetic twin is the estimated lift. The weight-fitting problem
is a QP:

```
min_w  sum_t (Y_treated,t - sum_j w_j*Y_j,t)^2      over the pre-period
s.t.   w_j >= 0,  sum_j w_j = 1
```

The simplex constraint forces the counterfactual to be an *interpolation*
of real donor geos, never an extrapolation — the whole reason to trust it
as "what would've happened without the campaign."

**The bug:** first implementation used
`scipy.optimize.minimize(SLSQP)` — a general nonlinear solver, reasonable
choice for a constrained optimization at a glance. But the donor geos here
are highly collinear (`geolift/simulate.py` builds them from one shared
macro factor), which makes the objective's curvature very uneven. Result:
SLSQP either failed its line search outright, or — worse — reported
success while landing on **-8.3% estimated lift against a true, injected
+8%**. Wrong sign, no error thrown.

**The fix** (`geolift/synthetic_control.py:27-58`), and why it's the
*right* fix rather than a patch: this QP is convex (least squares onto the
probability simplex), so it doesn't need a general nonlinear solver at
all — it needs a method built for exactly this shape. FISTA (projected
gradient descent + Nesterov momentum):

```python
step = 1.0 / (2.0 * spectral_norm(A)**2)     # fixed, below 1/Lipschitz — no line search to fail
w_new = project_to_simplex(y - step * grad)  # exact projection (Duchi et al. 2008), every step
```

No line search means no failure mode from uneven curvature — convergence
is monotonic regardless of collinearity, at `O(1/k^2)` instead of plain
projected gradient's `O(1/k)`.

**The honest finding layered on top:** even with the correct solver, a
single run is noisy — across 15 seeds the estimator is unbiased *on
average* (mean 7.6% vs. true 8%), but one seed's poor donor-pool fit
(pre-period RMSPE 9.5 vs. ~2.0 typical) flipped the point estimate's sign
again, *correctly this time* — meaning the fit itself was bad, not the
solver. That's exactly why `geolift/inference.py`'s placebo test
(Abadie/Diamond/Hainmueller 2010 rank permutation) and `pre_rmspe` exist:
a single point estimate is never trusted alone.
