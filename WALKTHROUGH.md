# Counterfactual — a Causal Decision Engine: Full Walkthrough

## 1. Why this project

Industry causal inference work clusters around a handful of recurring problems: who to target with an intervention (uplift modeling), whether a campaign that couldn't be cleanly A/B tested actually worked (geo-lift / synthetic control), and whether a new decision policy is worth risking a live experiment on (off-policy evaluation). This project builds all three as one coherent pipeline rather than three disconnected demos, because in a real company they *are* connected:

```
UPLIFT (individual)  ->  OPE (policy vetting)  ->  GEOLIFT (aggregate measurement)
"who to target"           "is this targeting         "did the real rollout
                            policy worth an             actually move the
                            A/B test slot?"              needle?"
```

A team decides who to target (uplift), cheaply checks whether that targeting rule would beat what's currently running before spending a real experiment on it (OPE), and — because the rollout often ends up being a blanket geo-level campaign rather than something randomizable at the individual level (TV, out-of-home, a national push) — measures whether it actually worked using synthetic control (geolift).

**Shared conventions** that hold the three modules together:
- Every estimator returns the same `EffectEstimate` dataclass — `{method, point_estimate, ci_lower, ci_upper, std_error, n, metadata}` — so results from wildly different methods (a CATE model, an OPE value estimate, a synthetic-control lift) are logged and compared identically.
- Every experiment is config-driven via pydantic-validated YAML (`configs/*.yaml`) — a new dataset, method, or hyperparameter set is a new YAML file, never a code change.
- Every pipeline script is runnable standalone (so each module is a complete, demoable thing on its own) *and* chainable (later scripts can load earlier scripts' saved artifacts).
- The uplift and OPE modules share one literal ground-truth reward function (`dgp_baseline_and_cate` in `common/io.py`) — so a policy trained on uplift's data is vetted, in OPE, against the same underlying business reality, not a different simulated world.

## 3. Module 1 — Uplift (who to target)

**Problem it solves:** given historical, randomized campaign data (an email blast, a discount, a promo), predict each customer's individual treatment effect (CATE) and turn that into a targeting rule, instead of treating everyone or no one.

**Method:** two meta-learners, built directly on scikit-learn (no causalml/EconML dependency, since causalml in particular is a common build-pain point on Windows):
- **T-learner** (`TLearner`): fit two independent regressors, one per arm — `mu0` on the control group, `mu1` on the treated group. `CATE(x) = mu1(x) - mu0(x)`. Simple, but can't share statistical strength across arms.
- **X-learner** (`XLearner`): same first stage, then a second stage imputes individual treatment effects (`D1 = Y - mu0(x)` for treated units, `D0 = mu1(x) - Y` for control units), fits models on those, and combines the two second-stage models weighted by an estimated propensity score. Better than T-learner when the arms are imbalanced in size.

**Evaluation** (`uplift/evaluate.py`):
- **Qini curve / AUUC**: rank the test population by predicted CATE, and at each fraction of the population targeted, compute the cumulative incremental outcome (treated outcomes minus control outcomes, rescaled for group-size imbalance within that slice). AUUC is the area between the model's curve and the random-targeting diagonal — the standard metric a targeting model is judged on.
- **Policy value** (`policy_value`): an inverse-propensity-weighted estimate of the average outcome *if everyone had received the treatment the policy prescribes*, valid because the actual treatment was randomized. This is the same IPW logic the OPE module reuses later for non-randomized logs.

**Policy** (`uplift/policy.py`): `UpliftPolicy` wraps a fitted CATE model plus a budget (`treat_fraction`) — it calibrates a score threshold on a held-out set so exactly that fraction gets treated, and serializes to `policy.joblib` so later stages (OPE) can load and evaluate the *exact* deployable policy without retraining.

**Data** (`common/io.py`, `generate_synthetic_uplift`): features `x0..x9` ~ N(0,1), randomized treatment (Bernoulli 0.5), and a known heterogeneous effect function:
```
baseline   = 1.0 + 0.5*x0 - 0.3*x2 + 0.2*x3
true_cate  = 2.0*max(x0, 0) + 1.5*(x1 > 0.5) - 0.5
outcome    = baseline + treatment * true_cate + noise
```
`true_cate` is kept in the dataframe but never used as a model feature — it's ground truth for testing, exactly analogous to how the geolift and OPE modules validate against a known truth rather than trusting a plausible-looking number.

**Run it:**
```
python pipelines/01_train_uplift_policy.py configs/uplift_synthetic.yaml
```
Writes `results/uplift_synthetic_v1/{summary.json, qini_curve.png, policy.joblib}`.

**Observed result:** AUUC ≈ 1117 (well above random targeting); predicted CATE correlates with true CATE at r > 0.3 in tests. One honest finding: the budget-capped policy (top 30%) scored *close to but not clearly above* "treat everyone" in raw policy value — because the synthetic reward has no treatment-cost term, so "treat everyone" looks artificially free. In a real business case you'd subtract a per-treatment cost, which is exactly what makes targeted uplift beat blanket treatment; left out here to keep the module a clean CATE/Qini demo.

## 4. Module 2 — OPE (is the new policy worth an A/B test?)

**Problem it solves:** you have a candidate targeting policy (e.g. module 1's output) and logs from whatever policy is *already* running in production. Before spending a live A/B test slot — with its cost and user-experience risk — estimate offline whether the candidate would actually beat the incumbent.

**Data** (`ope/simulate.py`, `generate_logged_bandit_data`): reuses the *same* `dgp_baseline_and_cate` ground-truth function as uplift, but treatment is now assigned by a **non-uniform logging policy** — `propensity = sigmoid(1.5 * proxy_score - 0.5)`, where `proxy_score` is correlated with but not equal to the true CATE driver. This is the realistic case: the production rule that generated your logs was never actually optimized for treatment effect. Propensities are clipped to `[0.05, 0.95]` to preserve overlap (no unit has literally zero chance of either action, which would make it unrecoverable by any OPE estimator).

**Estimators** (`ope/estimators.py`), all against a deterministic target policy (so the importance weight collapses to "1/propensity if the logged action matches the target policy's decision, else 0" — no logged reward can inform the target's value where the two policies disagree):
- **IPS** (inverse propensity scoring): `mean(match / propensity * reward)`.
- **SNIPS** (self-normalized IPS): `sum(weight * reward) / sum(weight)` — trades a little bias for much lower variance than plain IPS, standard practice when weights are noisy.
- **Doubly robust (DR)**: fits a direct-method reward model (reusing the uplift module's `TLearner` — literal code reuse across modules) on a training fold, then corrects it with an IPS-style term on a held-out evaluation fold: `q_hat(x, target_action) + (match/propensity) * (reward - q_hat(x, logged_action))`. Unbiased if *either* the direct-method model or the propensities are correct — hence "doubly robust."

All three report **bootstrap 95% CIs** (resampling rows) rather than derived analytic formulas — one consistent, correct approach instead of three different delta-method variances.

**Validation** (`ope/evaluate.py`, `ope/simulate.py::true_policy_value`): because the data is synthetic, the *exact* expected reward under any policy is computable directly from the known generating functions (`mean(baseline + target_action * true_cate)`) — no sampling noise. This is the rigorous way to validate an OPE estimator (the same spirit as the real-world Open Bandit Dataset benchmark, which ships a fully-random logging policy specifically so researchers can compute true on-policy value and check estimator accuracy against it, rather than just checking a number "looks plausible").

**Run it** (run phase 1 first — this loads its saved policy by default):
```
python pipelines/02_vet_policy_with_ope.py configs/ope_synthetic.yaml
```
Writes `results/ope_synthetic_v1/{summary.json, ope_comparison.png}`.

**Observed result:** vetting module 1's actual saved policy against logs from the (different) non-uniform logging policy: true target-policy value 1.724 vs. true logging-policy value 1.580. All three estimators landed within 0.02 of the true value, CIs all covered the truth, and the DR-based verdict correctly said "worth an A/B test."

**A real bug found and fixed here:** an early test asserted that `treat_all` would have a larger "effective sample size" (rows where the target policy's decision matches the logged action) than `treat_none`, reasoning that the logging policy "treats high-x0 units more often." That reasoning didn't account for the logging policy's overall base rate — the intercept in its propensity function actually makes it treat *fewer than half* the population on average, so `treat_none` in fact overlaps more. The fix: derive the majority/minority direction from the data itself (`majority_action = round(action.mean())`) instead of assuming a direction — a test that's correct by construction rather than by guess.

## 5. Module 3 — Geolift (did the rollout actually work?)

**Problem it solves:** measuring a campaign's effect when you can't randomize at the individual level — a TV spot, an out-of-home campaign, a blanket geo-level push notification. The unit of "randomization" becomes geography instead of the user.

**Method — synthetic control** (`geolift/synthetic_control.py`): build a weighted combination of untreated donor geos that best tracks the treated geo's *pre-campaign* trend, then the gap between the treated geo's actual post-campaign outcome and that synthetic twin's predicted (no-campaign) outcome is the estimated lift. The weight-fitting problem is a constrained least-squares QP:

```
min_w  sum_t (Y_treated,t - sum_j w_j * Y_j,t)^2      over the pre-period
s.t.   w_j >= 0,  sum_j w_j = 1
```

The non-negativity + sum-to-one constraints force the counterfactual to be a convex combination (weighted average) of real donor geos — an interpolation, never an extrapolation — which is the whole point (it's what keeps the "synthetic geo" grounded in geos that actually exist, unlike unconstrained regression, which would allow negative weights and overfit noise).

**Solver — FISTA, not SLSQP (a real bug found and fixed):** the QP was first implemented with `scipy.optimize.minimize(method="SLSQP")`, a general-purpose nonlinear solver. Donor geos here are highly collinear (they all share one underlying macro factor in the simulator), which makes the objective's curvature very uneven — and SLSQP either failed its line search outright (`Positive directional derivative for linesearch`) or, worse, "succeeded" while returning an answer with the **wrong sign** (estimated -8.3% lift against a true +8% injected effect). Since this is a genuinely convex problem, the fix was to stop using a general nonlinear solver and use one built for exactly this shape: **projected gradient descent onto the probability simplex**, accelerated with Nesterov momentum (FISTA) for faster convergence. No line search to fail — a fixed step size below `1/Lipschitz` plus an exact simplex projection (`_project_to_simplex`, the Duchi et al. 2008 algorithm) converges monotonically regardless of collinearity.

**Inference** (`geolift/inference.py`): with only a handful of geos, there's no valid normal-theory standard error. Instead, **placebo tests** (Abadie, Diamond & Hainmueller 2010's rank permutation test) — refit the exact same procedure pretending each *control* geo was the treated one, compute each geo's post/pre RMSPE ratio, and see how unusual the real treated geo's ratio is against that placebo distribution. `placebo_p_value` = fraction of geos (including the real one) whose ratio is at least as extreme.

**Data** (`geolift/simulate.py`, `generate_geo_panel`): no public geo-marketing dataset ships a known ground-truth lift, so validation here is **recovery accuracy**: correlated donor trends built from a shared stochastic common factor with geo-specific loadings/levels/trends (similar-but-not-identical series, like real regional data), with a known percentage lift injected multiplicatively into the treated geo's post-period outcomes.

**Run it:**
```
python pipelines/03_measure_rollout_geolift.py configs/geolift_synthetic.yaml
```
Writes `results/geolift_synthetic_v1/{summary.json, geo_trajectory.png}`.

**Observed result:** true injected effect +8.0%, synthetic control recovered +8.97%, placebo p-value 0.048. Checked across 15 random seeds, the estimator is unbiased *on average* (mean 7.6% vs. true 8%), but any single run is noisy — one seed's poor donor-pool fit (`pre_rmspe = 9.5` vs. ~2.0 typical) even flipped the estimate's sign. This is exactly why practitioners check pre-period RMSPE and lean on placebo tests rather than trusting any single point estimate — and it's why the test suite checks unbiasedness averaged across seeds, plus a separate test that a *good* pre-fit (low RMSPE) does recover the effect tightly, rather than asserting tight accuracy on one arbitrary run.

## 6. Integration — the full chain

`pipelines/04_full_pipeline.py` runs all three phases in order (via subprocess) and — critically — makes the geolift stage's injected effect size a **derived** number, not an arbitrary config value:

```python
pct = (dr_estimate.point_estimate - empirical_logged_reward) / empirical_logged_reward
pct = clip(pct, -0.5, 0.5)
```

That is: "what OPE's doubly-robust estimator said the new policy would do to the topline metric, relative to what's running today, using only data a team would actually have in hand before deciding to roll something out." This gets written to `configs/geolift_rollout.yaml` (so the derivation is inspectable, not hidden), and geolift then measures a simulated rollout against exactly that expectation — closing the loop from "who to target" through "is it worth testing" to "did it work."

**Run it:**
```
python pipelines/04_full_pipeline.py
```
Writes `results/full_pipeline_v1/{summary.json, report.html}` — open `report.html` in a browser for a combined write-up embedding all three modules' plots plus a bottom-line table.

**Last observed run:** OPE derived a +8.5% expected lift from the vetted policy vs. current production; geolift's synthetic control, measuring the simulated rollout independently, recovered +9.5% (placebo p = 0.048).

**Another real bug found and fixed here:** `Path.write_text()` defaults to the OS locale encoding on Windows (cp1252), not UTF-8 — this silently mangled the report's em dashes (`—` became `�`) even though the HTML declared `charset="utf-8"`. Fixed by writing explicitly: `write_text(report_html, encoding="utf-8")`.

## 8. Testing philosophy

Every test checks recovery of a **known ground truth**, not just "the code runs without an exception":

| Test file | What it actually checks |
|---|---|
| `test_uplift_qini_beats_random.py` | AUUC > 0 (beats random targeting), predicted CATE correlates (r > 0.3) with the synthetic generator's true CATE, treatment is genuinely ~randomized (45-55%) |
| `test_synthetic_control_recovers_known_effect.py` | Weights form a valid convex combination; estimator is unbiased *on average* across 15 seeds; a good pre-fit (low RMSPE) recovers the injected effect tightly; a true-zero effect does not produce a falsely significant placebo p-value |
| `test_ope_estimator_bias.py` | Logged reward matches the true logging-policy value (simulator sanity check); IPS/SNIPS/DR all land within 5pp of true policy value under full and partial overlap, with CIs covering the truth; effective sample size is provably larger for the majority-matching policy |

11/11 tests pass as of the last run (`pytest -q` → `11 passed`).

## 9. Known limitations / natural next steps

- **Uplift**: no treatment-cost term in the reward model, so "treat everyone" can look artificially competitive with a budget-capped policy. Adding a per-treatment cost would make the targeting story sharper.
- **OPE**: the DR estimator uses a single train/eval split rather than full cross-fitting (would reduce variance further, more code).
- **Geolift**: validated only against a synthetic panel (no public dataset ships known ground-truth lift); a secondary sanity check against a classic real dataset (e.g. Abadie's California Prop 99 panel) is a natural addition.
- **Real datasets**: `configs/uplift_hillstrom.yaml` is a template — drop a real Hillstrom/Criteo CSV into `data/raw/` to run the uplift module on real campaign data instead of the synthetic generator.
- **Not version-controlled yet** — no `git init` has been run in this directory.
